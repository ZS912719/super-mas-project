# Reply-Quality Benchmark

Measures whether the drafted replies are right, for one model configuration at a time, so the effect of the **model** and of **our system** can be separated (step 13). Runner: `src/test/java/org/supermas/prototype/ReplyQualityBenchmark.java`; checks: `ReplyChecks.java`; tests: `ReplyChecksTest.java`.

## Design: a 2×2

| | 3 B model | 8 B model |
| --- | --- | --- |
| System as it is (baseline) | A | B |
| After the system fixes (excerpt relevance, email details marked as known, missing information from the knowledge) | C | D |

A vs B is the model's effect, A vs C the system's, D what is reachable. The template (no model) is the floor. Development results only: the fixes are designed from A/B on the same 36 emails, so C/D need a fresh set before they count (to-do 3.6). Final numbers must come from the local model (to-do 2.6).

## Data and expectations

The 24 `synthetic-dev` and 12 `synthetic-multi` emails. Each has a frozen `<email>.reply.json` (schema `reply-gold/v1`, generated by `benchmark/write_reply_gold.py`, committed in `451a654` **before any model run**, written by the AI assistant from the six knowledge documents; **reviewed by the owner on 2026-11-11: 36 of 36 confirmed unchanged**, verdicts in `<email>.reply.review.json`, protocol B52; a second reader is still open):

| Field | Meaning |
| --- | --- |
| `language` | `en` or `fr`: the reply must be in the email's language |
| `replyExpected` | `false` for notices, broadcasts, thank-you notes and the owner's own sent mail (10 of the 24 dev emails); those are reported separately |
| `greet` / `notGreet` | Names of which one must, and none may, appear in the greeting line (`greet: null`: any greeting) |
| `mustMention` | Facts from the knowledge the reply must state; each satisfied by any of its terms |
| `mustAsk` | What the reply must ask the sender for: a sentence with the term that is a question or carries an asking cue ("please", "could you", "send", "merci de", ...) |
| `mustNotContain` | Forbidden phrases: promises and decisions for the owner, the sender's own data repeated back, unrelated knowledge ("noise") |
| `allowInternal` | `true` for staff senders, who may see the staff-only marking guide |

Checks on every reply: a bracketed placeholder (`[Your Name]`) is a violation; text of the staff-only marking guide is a violation unless `allowInternal`; since revision 2, a name after the closing (`signature`: a last line of at most four words after "Best regards," and similar) is a violation.

**Revision 2** (2026-11-07, after runs A and B, approved by the owner): the greeting check had accepted only first names, so "Dear Mr. Ruiz" counted as wrong; each sender's last name is accepted now (`"revision": 2` in every file, change in `benchmark/write_reply_gold.py`), and the signature check was added. Because this was decided after seeing results, A and B are reported with both revisions (`--rescore`, below). Matching ignores case, accents and apostrophe variants.

**Limits.** Keyword checks find a missing fact or a forbidden phrase reliably, but they cannot see tone, a true fact used wrongly, or a correct paraphrase with other words (a false negative). Read `drafts.md` and score a sample with the rubric of to-do 3.2; treat the automatic numbers as indicators.

## Running

Model settings as for the prototype (`docs/plans/llm-setup.md`). One fresh data folder per set and repeat; emails in file order; every reply recorded under the label folder, so a run can be replayed without a model.

```bash
# run A: the 3 B model, system as it is
SUPERMAS_LLM_MODEL=meta-llama/llama-3.2-3b-instruct mvn -q test-compile exec:java -Dexec.classpathScope=test -Dexec.mainClass=org.supermas.prototype.ReplyQualityBenchmark -Dexec.args="--label A-3b"
# run B: the 8 B model
SUPERMAS_LLM_MODEL=meta-llama/llama-3.1-8b-instruct mvn -q test-compile exec:java -Dexec.classpathScope=test -Dexec.mainClass=org.supermas.prototype.ReplyQualityBenchmark -Dexec.args="--label B-8b"
```

Defaults: dev once, multi twice (`--dev-repeats`, `--multi-repeats`), output `runtime/reply-benchmark/<label>/` (ignored by Git): `results.md` (summary, violations by kind, per email), `drafts.md` (every draft with its checks and explanation), `scores.jsonl`, `llm-cache/`. An existing label folder is refused, so runs never mix. To score a run's saved replies again with the current checks, without a model: `--label A-3b-checks2 --rescore runtime/reply-benchmark/A-3b`. To re-run the system on recorded replies (only exact prompt matches answer): `--label A-3b-replay --llm-provider replay --llm-model <same model> --llm-cache runtime/reply-benchmark/A-3b/llm-cache`.

Ablation options (benchmark plan W3), one change at a time: `--composer-prompt FILE` (variants in `benchmark/prompt-variants/`), `--architecture router` (the step 11 router instead of the blackboard), `--knowledge DIR` (`benchmark/knowledge-variants/none` runs without knowledge documents). Single-agent baseline (plan W2): `--single-agent benchmark/prompt-variants/single-agent.txt` replaces the whole system by one model call per email (`common.txt` plus that prompt, the email and every knowledge document, with no metadata, routing, retrieval or access control), through the same output guards and checks. Compare configurations over repeated runs with `scripts/benchmark/compare_runs.py` (protocol B42).

About 36 + 12 = 48 model calls per run with the defaults (the composer makes one call per email).
